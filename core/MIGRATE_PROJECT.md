# Moving Setu to a Supabase project you own

The project the three apps point at today — `idngqijhodyahdgodybt` — belongs to
an account you do not have credentials for. This is how you stand up your own
and repoint everything at it.

Nothing here needs Homebrew, `psql` or a global CLI install. SQL goes in the
dashboard's SQL editor; the CLI runs through `npx supabase`.

Budget an hour or so. Work top to bottom — later steps depend on earlier ones.

## Before you start: the keys you may also be missing

Supabase is not the only account involved, and the same problem may apply to
each of these. Check now rather than at step 7:

| Secret | What it does | If you don't have it |
|---|---|---|
| `RESEND_API_KEY` | delivers the OTP email | Sign-in is dead. Free tier is enough — see step 7. |
| `GEMINI_API_KEY` | Ask Setu's answers | Ask Setu returns an error; everything else works. |
| `ELEVENLABS_API_KEY` | Kannada speech in and out | Voice is dead; `speech_to_text` still covers the offline fallback. |

`SEND_EMAIL_HOOK_SECRET` is generated by your new project in step 6, so that
one you will always have.

The Resend one has a second half people miss: a **verified domain**. Without
one, Resend refuses every recipient except the address that owns the Resend
account, so exactly one of your demo logins works and the rest silently fail.

## 2. Build the SQL

```bash
cd /Users/mac/Documents/DSU/setu
./core/bootstrap_new_project.sh
```

Writes two files into `build/`. The order inside them is load-bearing: columns
are added by one file and inserted into by another four files later, so the
script encodes the order once rather than leaving you to paste fifteen files in
the right sequence.

## 3. Run the schema

Either paste it into the SQL editor:

```bash
pbcopy < build/bootstrap_1_schema.sql     # then New query -> paste -> Run
```

or, with a personal access token, run it from here:

```bash
export SUPABASE_ACCESS_TOKEN=sbp_...
python3 core/run_sql.py <ref> build/bootstrap_1_schema.sql
```

`run_sql.py` goes through the Management API, which takes the file as one
batch exactly as the SQL editor does — so a file that works in one works in
the other. It prints the Postgres error on failure, which the dashboard buries.

Expect `OK` / `Success. No rows returned`.

## 6. Auth

**Authentication → Sign In / Providers → Email**, or by API. Three settings,
and the first one is not optional:

- **Email OTP length: 6.** A new project defaults to **8**. Every app caps the
  code field at `maxLength: 6` and rejects anything else, so an 8-digit code is
  literally untypeable — sign-in fails everywhere with no useful error.
- **Email OTP expiration: 600 seconds.** Default is 3600. Every OTP email says
  the code expires in 10 minutes; leave it at an hour and the email is lying.
- Email provider on. Leave "Confirm email" as it is — the OTP flow confirms the
  address by the code being entered, so it works either way.

By API, **one field per call**:

```bash
API=https://api.supabase.com/v1/projects/<ref>/config/auth
curl -X PATCH "$API" -H "Authorization: Bearer $SUPABASE_ACCESS_TOKEN" \
  -H "Content-Type: application/json" -d '{"mailer_otp_length":6}'
curl -X PATCH "$API" -H "Authorization: Bearer $SUPABASE_ACCESS_TOKEN" \
  -H "Content-Type: application/json" -d '{"mailer_otp_exp":600}'
```

Send several fields in one PATCH and if any one of them is not settable the API
discards the **whole** patch — and still answers 200 with the full config, so it
reads as success. Always GET afterwards and check the value actually moved.

`rate_limit_email_sent` is one of those unsettable ones while the built-in
sender is in use. It sits at 2 per hour, a real constraint on a demo with eight
logins — it lifts once the send-email hook takes over in step 7.

The Send Email hook itself is step 7's script, not a manual setting. Enabling
it before the function holds its secrets points Auth at a function that answers
500, and every sign-in fails until that is undone.

## 7. Deploy the functions

```bash
cd /Users/mac/Documents/DSU/setu/thayi

npx supabase login                       # opens your browser, one time
npx supabase link --project-ref <your new ref>

npx supabase secrets set \
  RESEND_API_KEY=re_xxx \
  SEND_EMAIL_HOOK_SECRET='v1,whsec_xxx' \
  OTP_FROM_ADDRESS=no-reply@<your verified domain> \
  GEMINI_API_KEY=xxx \
  ELEVENLABS_API_KEY=xxx
```

`SUPABASE_URL` and `SUPABASE_SERVICE_ROLE_KEY` are injected by the platform —
do not set those yourself.

Do **not** set `OTP_FROM`. It overrides the per-app sender name, so every code
would go out as Thayi Setu again.

Then all four functions at once:

```bash
cd /Users/mac/Documents/DSU/setu
./core/deploy_functions.sh <your new ref>
```

`send-email` lives under `thayi/supabase/` and the other three under
`core/functions/`, so the CLI can never see all four from one directory. The
script stages them into a temporary tree and deploys from there, without
copying anything into the repo. It also passes `--use-api`, which bundles
server-side — the CLI otherwise wants Docker, which is not installed here, and
fails with a daemon error that reads like a CLI bug.

Finally, hand OTP mail over to the branded function — **only** once Resend has
a verified domain:

```bash
./core/enable_email_hook.sh <ref> re_xxx no-reply@<your verified domain>
```

It sets the function's secrets, waits until the function stops answering 500,
and only then flips the hook — so there is no window where Auth is pointed at a
function that cannot send. Until you run it, Supabase's own sender delivers a
plain unbranded code: working sign-in, no logo.

## 8. Point the apps at it

```bash
cd /Users/mac/Documents/DSU/setu
./core/point_apps_at_project.sh https://<ref>.supabase.co sb_publishable_xxx
```

That writes `.env` at the repo root — gitignored, read by all three apps at
build time. One file rather than three `env.dart` edits, so two apps cannot end
up on one project while the third is still on another; that failure looks like
an RLS bug rather than a config mistake.

Nothing to commit here: the credentials never enter the repo. `.env.example`
is the tracked copy that shows the shape.

## What does not move

Auth users. Anyone who signed in on the old project has an `auth.users` row
there, not here. They are recreated on first sign-in, and step 4's triggers
link each one to its `mothers` or `staff` row by email — so there is nothing to
export, as long as people sign in with the same addresses.
